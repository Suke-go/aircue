# v0.6 初期実験案と実行環境の選択

## 実行環境は研究に合わせて選ぶ

実験計画・因子表・試行順・完成WAVはUnityに依存しない。標準はAirCue単体の実行と回答記録、またはWAV・JSONの汎用書き出し。Python、PsychoPy、自作アプリなどを使う場合も同じ実験データを読める。Unityは任意の連携先の一つであり、実験実施の前提条件ではない。他環境の専用アダプターや回答画面は同梱していない。

## 研究を始める順序

1. **キャリブレーション**: イヤホン左／右、空気刺激左／右を単独提示し、左右識別と接続を確認する。小さい基準レベルから、参加者が快適と答える音・空気刺激レベルへ調整する。左右それぞれ2〜4回程度の確認試行を行い、違和感があれば停止する。左右を取り違えたまま本試行へ進めない。
2. **探索実験**: まず「単独刺激と複合刺激」の6条件（左右 × audio only / puff only / combined）を4反復、24試行。combinedは整合・開始差0 ms。方向の識別可能性、快適さ、回答方法を確認する。必要に応じて別の短いセットで左右整合性4条件 × 4反復＝16試行、または開始差6条件 × 4反復＝24試行を調べる。全テンプレートを一括で交差させない。
3. **本実験**: 探索結果に基づき、事前に決めた主仮説に必要な条件だけ採用する。各条件の総反復を4〜8回にし、各ブロック内でランダム化する。例: 全因子が必要なら単独刺激4条件＋combined 12条件（音の左右2 × 整合／不整合2 × 開始差−100/0/+100 msの3）＝16条件。2ブロック、ブロック内2〜4反復で計64〜128試行。UIの「反復」は**各ブロック内**の回数なので、総反復との二重計上を避ける。

整合性だけが主仮説なら開始差0に固定し、単独4＋combined4＝8条件、32〜64試行へ減らせる。開始差が主仮説ならcombinedを整合に固定し、単独4＋combined6＝10条件、40〜80試行にする。休憩はブロック間に設け、疲労や慣れが強ければブロックを短くする。サンプルサイズは探索時の効果・ばらつきと事前の解析計画から決め、この試行数だけで検出力を保証しない。

主指標は方向判断または反応時間を1つ選ぶ。方向判断では `left/right/front/back/uncertain` を使い、試行ごとの反応時間も保存する。反応時間は最初に予定された刺激開始から回答まで。負の開始差では空気刺激が基準になる。主解析の基準時点を音開始にする場合はmanifestの条件と予定時刻から別途算出し、解析計画に明記する。補助指標は強さ・自然さ・快適さから必要なものだけ選ぶ。実装上の尺度は0〜10。AirCueのJSONLでは未選択指標を省略し、Unity APIでは未選択を−1で渡す。左右回答を強制して不確実さを失わないようにする。

## 実装したテンプレート

| template | 因子表 | 条件数 |
|---|---|---:|
| `modality` | 音／空気／複合 × 左右、複合は整合・0 ms | 6 |
| `congruency` | 音の左右 × 空気刺激の同側／反対側、0 ms | 4 |
| `onset` | 左右整合 × −100/0/+100 ms | 6 |
| `intensity` | 左右整合 × 基準から−6/−3/0 dB、0 ms | 6 |

知覚強度テンプレートの値はデジタルゲインの操作であり、知覚強度の等間隔性やdB SPLを意味しない。基準はキャリブレーションで確かめた快適レベルにし、テンプレートは増幅せず減衰する。現版の強度因子は音と空気刺激の両方に同じ補正を加える。片方だけの強度操作、個別の実測補正は次の実装範囲。

## 基準刺激と因子表

基準のタイムラインは音声1クリップ（10秒以内）、空気刺激1クリップ。元のタイムラインを変更せずに、条件ごとの別Projectを生成する。音源・切り出し・再生時間・距離・基準音声レベル・波形・クリップ補正を引き継ぎ、条件生成時に音の位置を左右の耳の水平面に固定する。基準の移動経路や配置時刻を実験刺激に引き継ぐものではない。複雑な時間列はタイムラインのWAV書き出し／ローカル連携を使用する。

`onsetDiffMs = airStart − audioStart`。正は空気刺激が後。全条件で音開始の基準はWAV先頭から200 ms、空気刺激は200＋開始差 ms。単独刺激には開始差0のみ許可する。各条件の終端は同一で、余白を含む。WAVの48 kHzサンプル時刻はデジタル出力の設定で、物理的な音・噴流の開始差ではない。実測遅延を用いた補正と測定手段は本実験前に別途決める。

「因子表を確認・編集」で次の形式の配列を編集できる。モダリティに存在しない側は `none`、条件IDは重複のない英数字・下線・ハイフン40文字以内。Windowsのファイル名衝突を防ぐため、大文字小文字だけが違うIDと `calibration-` で始まるIDは使えない。

```json
[
  {"id":"audio-left","modality":"audio","audioSide":"left","airSide":"none","onsetDiffMs":0,"gainDb":0},
  {"id":"puff-right","modality":"air","audioSide":"none","airSide":"right","onsetDiffMs":0,"gainDb":0},
  {"id":"incongruent-early","modality":"combined","audioSide":"left","airSide":"right","onsetDiffMs":-100,"gainDb":0}
]
```

参加者IDは `P001` のような匿名IDにする。氏名等との対応表は別管理し、manifest／ログへ含めない。64参加者・32条件・各ブロック1〜8反復・1〜16ブロック、全体32768試行まで。シード・参加者ID・ブロック番号をSHA-256で種にし、SplitMix64とFisher–Yatesで順序を固定する。同じ入力から同じ順序を再生成でき、参加者を追加しても既存参加者の順序は変わらない。完全なカウンターバランスや連続同条件を避ける制約付きランダム化は未実装。

## 保存と固定内容

「条件と試行順を生成」でProjectのコピーを固定し、「manifestを保存」でJSON形式の `.aircueexp` に保存する。Projectとは別のファイルであり、プロジェクトの自動保存には含まれない。manifestを開いても現在のProjectやルーティングを上書きしない。出力元と同じProject・音声素材に戻すか、読み込んだ因子表から現在のProjectで再生成して書き出す。

- `schemaVersion: 1` と生成アプリ版（v0.6.0）
- `projectHash`: v0.5のprepareと同じProjectのJSONに対するSHA-256
- `mediaHashes`: 使用する変換済み音声WAVのSHA-256
- `stimuli`: 条件IDを刺激IDとし、Project・素材ハッシュ・生成版によるリビジョン、完成Sequenceへの相対パス、ルーティング・波形レベル・クリップ補正を保持
- `hrtfMode`: `baked-stereo/mit-kemar-48000-140`
- `deviceInfo`: 生成時の選択機器ID・表示名・ホスト・チャンネル情報。機器未選択とCLIではnull。Project内の選択機器ID・ルーティングも保持
- `plan` と `trials`: 因子表、測定項目、匿名参加者、反復・ブロック・実際の試行順

読み込み時はフィールド、因子、ハッシュと再生成した順序を検証する。異なる生成アプリ版のmanifestは拒否し、将来のレンダリング変更を暗黙に混ぜない。ハッシュは再現性の確認であり電子署名ではない。デバイス情報は作成環境の記録であって他の実験環境に同じ機器を自動選択させる設定ではない。

## AirCue単体での実行

1. 出力設定で4ch機器を選び、実験セットを生成する。「AirCueで実行」で匿名参加者を選び「参加者を準備」。準備では再生しない。全条件を事前レンダリング検査し、現在のProject・素材がmanifestと一致することを検証する。
2. セッション内のイヤホン左／右・空気刺激左／右の4ボタンを順番に再生する。再生完了後、左右と快適レベルの3項目を実際に確認して「確認を記録」。レベルや機器を変更する場合は一度セッションを終了し、調整・再生成後に確認をやり直す。
3. 「次の試行を再生」で固定した順序の次試行を提示する。方向判断または「感じた」のボタンで主回答を記録する。補助評定の入力時間を反応時間に含めない。刺激の再生終了後に評定を入力し「この試行を保存」。自動連続再生はせず、ブロック表示を見て必要な休憩を取る。
4. 「この試行を中止」は理由と既存の主回答を記録し、その試行を消費する。セッション終了・アプリ終了も未完了試行を中止として記録する。クラッシュや強制終了は終了イベントを残せないため、末尾が未完了のログは不完了として扱う。中断後の再開機能はなく、同じ参加者を再び準備すると別セッションで先頭から始まる。

記録はAirCueのデータフォルダー内 `study-results/<participant>-<session>.jsonl`。最初のイベントに完全なmanifestと実行機器、その後に確認、試行、回答、評定、中止を保存する。回答時刻はバックエンド受信時点の単調時計。刺激開始は音声エンジンのフレーム進捗から推定し、約5 ms間隔で観測する。OSのスケジューリングや音声バッファ、UIからの通信遅延を含むため精密な物理反応時間の測定器ではない。`plannedOnsetOffsetMs` はWAV先頭からの予定開始、`startedObserved` 内の時刻はソフトウェア観測／推定として区別する。記録失敗時は出力を停止し、エラーを表示する。

セッション中はProject編集・別プレビュー・外部連携開始を拒否し、設定混在を防ぐ。ヘッドホンのみの条件も同じ4chストリームで提示する。参加者用の全画面表示や外部ボタン、正確な音声出力タイムスタンプ、セッション途中再開は未実装。

## 任意の実験環境へ渡す

「WAV・JSONを書き出す」でUnityファイルを含まない新規フォルダーを作る。`Experiment.aircueexp` と `Sequence.aircueseq` はどちらもUTF-8 JSON。4ch WAV、ヘッドホン2ch、左右各1ch、確認刺激を同梱する。各環境での読込規則・チャンネル対応・ログ要件は [EXPERIMENT_BUNDLE.md](EXPERIMENT_BUNDLE.md) を参照。

現在のタイムラインをAirCueの出力機器で鳴らす場合は、任意のTCPクライアントから [ローカル連携](EXPERIMENT_SYNC.md) のJSONプロトコルも利用できる。この方式の試行順・回答は呼び出し元で管理する。

## Unityでの実行（選択した場合のみ）

1. 「Unity連携（任意）」内の「Unity用Bundleを書き出す」で新規フォルダーを生成する。保存済みProject・素材と現在の内容が違えば拒否する。
2. 内部の `AirCueUnity` を検証用Unityプロジェクトの `Assets` へコピーする。全条件のSequence、4種類の左右確認音、manifest、`checksums.json` を含む。WAVは従来の同じRustレンダラーによる完成音響。
3. `Experiment.aircueexp` をシーンへドラッグする。Importerが各Sequenceの依存を登録し、`AirCueExperimentSet` と `AirCueExperimentRunner` のPrefabを作る。自動再生しない。Audio Listenerと実際の4ch出力を設定する。
4. 実験スクリプトから `BeginParticipant("P001")`。`PlayCalibration(0..3)` がイヤホン左／右・空気刺激左／右。実際に左右・快適さを確認して `ConfirmCalibration(true,true,true)`。参加者の変更、再起動、出力構成の変更後は再確認する。
5. `PlayNext()` でその参加者の次試行。回答は `SubmitResponse("left", -1, -1, -1)` などで渡す。補助指標を選んだ場合は対応する0〜10の値が必須。方向判断のみなら `SubmitDirection("left")`、反応時間のみなら `SubmitReaction()` も使える。回答UIと休憩画面は研究側が用意する。
6. 中止は `Abort("participantRequested")` などで理由を記録する。中止試行は消費され、自動で同じIDを再試行しない。再試行の扱いを解析計画で決める。

空気刺激を含む本試行はRoutedQuad必須で、Headphonesでは開始を拒否する。Unityの機器と端子対応を実測で確認する。AirCueのローカル実験サーバーと同時再生しない。ExperimentClientの`current`限定仕様は変更していない。

ログは `Application.persistentDataPath/aircue-<sessionId>.jsonl`。セッション・匿名参加者・試行・条件・刺激ID、リビジョン、projectHash、予定Unix時刻／DSP時刻、Unityフレームでの開始観測DSP時刻、回答DSP時刻、結果・反応時間、選んだ評定、中止理由、実行出力構成を残す。未観測時刻は−1。`startedObserved`はUpdateでの観測なので物理刺激開始でも音声コールバックの時刻でもない。数値から1 ms精度の物理同期を主張しない。ログ書き込み失敗を成功扱いせず、予定記録に失敗したときは再生を止める。

CLIで検証用の既定セットも生成できる:

```powershell
AirCue.exe --export-experiment project.aircue destination onset
```

Unity用ファイルも必要な場合は `--export-experiment-unity` を明示する。通常の `--export-experiment` はWAV・JSONのみ。

このCLIの既定はP001・seed42・4反復・1ブロック・方向判断・補助指標なし。通常の研究設定は画面で編集・保存する。

## 次に判断する事項

まず探索の主指標を方向判断とするか反応時間とするか、補助指標を1つ付けるかを決める。次に本実験で整合性と開始差を同時に扱う必要があるかを決め、8／10／16条件のどれにするか選ぶ。物理的な開始差を主張する前に、音と空気刺激の実測方法、参加者の快適レベルの運用、休憩・中止・欠測の扱いを確定する。
